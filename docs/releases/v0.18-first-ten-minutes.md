# v0.18 first-ten-minutes observation protocol

Issue: #5902  
Parent experience contract: #5900  
Installed candidate acceptance: #4346

## Purpose

This protocol adds a bounded observation layer to the automated provider,
readiness, freshness, and package receipts. It asks whether the first installed
experience is legible and useful without turning one observer's judgment into a
score or a permanent telemetry programme.

The instrument validates the observation packet. It does not launch VS Code,
observe a user, repair findings, or authorize a release.

## Two-pass placement

Run the same finite protocol twice:

```text
pre_freeze_release_shaped
  discover product and first-mile blockers before the product SHA freezes

exact_candidate_confirmation
  confirm that preparation, synchronization, and packaging did not change the
  accepted experience
```

A product failure in the second pass invalidates the affected product evidence.
It is not converted into release-instrument noise merely because it was found
late.

## Representative project families

Every receipt binds one content-addressed fixture from exactly one family:

- `conventional_modules`;
- `test_heavy`;
- `framework_shaped`;
- `environment_sensitive`;
- `dynamic_boundary_control`.

The complete v0.18 study uses a finite set covering all five families. One
receipt intentionally proves only one fixture/candidate/platform observation.

## Four required journey steps

| Step | User activity | Required evidence |
| --- | --- | --- |
| `install_startup` | install, select the managed binary, start, and reach useful readiness | artifact identity, lifecycle transitions, interventions, notifications |
| `understand_project` | completion, hover, navigation, symbols, diagnostics, and one discoverable action | first useful/correct timings and provider outcomes |
| `change_project` | edit, create/delete/rename where safe, re-query, format, and rename or refuse | generation/freshness, exactness, and edit-safety evidence |
| `diagnose_recover` | inspect status/doctor, exercise one bounded problem, restart, and shut down | actionability, recovered identity, and process cleanup |

The validator rejects missing or duplicate steps.

## Trust-breaking counts

The following are load-bearing and must always be explicit:

```text
false_exact
stale_exact
unsafe_edit
unexplained_empty
silent_startup_failure
broken_documented_install
wrong_binary_or_version
orphaned_server_or_debuggee
```

Any non-zero trust-breaking count computes `blocked`, regardless of a hand-written
status. Notification and intervention counts are observations rather than release
blockers by themselves.

## Friction classes

```text
broken
trust_breaker
actionability
discoverability
noise
latency_or_readiness
consistency
polish
expected_beta_boundary
not_proven
```

`expected_beta_boundary` records honest fallback, refusal, or preview limits and
does not block by itself. `broken` and `trust_breaker` block. `not_proven`
prevents a pass. Reproducible findings are routed to an existing exact owner or
a bounded leaf issue; the protocol must not create a generic polish backlog.

## Validation

Run the example validator against a receipt:

```bash
cargo run -p xtask --example first_ten_minutes -- \
  --receipt fixtures/experience/first_ten_minutes/valid.json
```

Run its negative-direction tests:

```bash
cargo test -p xtask --example first_ten_minutes
```

The checked-in negative fixture proves that a stale exact result and failed
post-edit step compute `blocked`.

## Claim boundary

A validated receipt establishes that one exact packaged candidate, clean editor
profile, platform, and content-addressed fixture were observed through the four
required steps with explicit trust counts and friction routing. It does not
establish all-project, all-framework, all-editor, all-platform, or broad DAP
quality, and it carries no release authority.
