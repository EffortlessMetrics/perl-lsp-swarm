# v0.18 release topology

`release_topology.v1` is the exact-SHA inventory consumed by release
preparation, install-transition rehearsal, artifact integrity, and channel
verification. It is an inventory, not a release-readiness verdict and not
permission to publish.

`release_topology.v2` is an explicit opt-in that adds the public archive checksum
inventory. The generator still defaults to v1, and existing workflows continue
to request v1. The v1 schema and historical manifest bytes are unchanged; a v1
manifest never establishes the new checksum-inventory claim.

Install the pinned validator before local generation:

```powershell
python -m pip install --only-binary=:all: -r scripts/requirements-release.txt
```

Generate the frozen inventory from the exact frozen checkout `F`:

```powershell
python scripts/generate_release_topology.py `
  --release 0.18.0 `
  --frozen-product-sha <40-hex-freeze-sha> `
  --output release_topology.frozen.v1.json
```

After deterministic preparation produces the exact checkout `P`, generate its
projection by consuming the reviewed frozen bytes and digest explicitly:

```powershell
python scripts/generate_release_topology.py `
  --release 0.18.1 `
  --frozen-product-sha <40-hex-freeze-sha> `
  --prepared-swarm-sha <40-hex-prepared-sha> `
  --frozen-root <exact-frozen-checkout> `
  --frozen-topology release_topology.frozen.v1.json `
  --frozen-topology-sha256 <64-hex-frozen-topology-digest> `
  --output release_topology.v1.json
```

The generator derives the crate allowlist and topological order from Cargo
metadata, the binary target/archive matrix from `.github/workflows/release.yml`,
the VSIX identity from `vscode-extension/package.json`, and source hashes from
the checkout, including every workspace member's `Cargo.toml` and the exact
selected `schemas/release_topology.v1.schema.json` or
`schemas/release_topology.v2.schema.json` bytes used for validation. The
selected `--root` checkout supplies that schema authority; frozen and prepared
checkouts must bind identical committed schema bytes. Prepared
comparison preserves the topology input files and only normalizes explicitly
version-derived metadata fields; it does not claim whole-tree source
invariance. Every topology input must be tracked and clean in its declared
checkout; generated output manifests may remain untracked. It refuses to emit
a manifest when any of those authorities disagree. In particular, the current
tree cannot supply v0.18 evidence until the workspace and extension are prepared
as the requested version. Source generation at another matching version remains
an inventory observation, not a v0.18 freeze or release-readiness verdict.

Validate an existing manifest against the exact checkout and freeze SHA:

```powershell
python scripts/generate_release_topology.py `
  --check `
  --release 0.18.0 `
  --frozen-product-sha <40-hex-freeze-sha> `
  --output release_topology.frozen.v1.json
```

For a prepared check, retain the same frozen authority arguments used for
generation:

```powershell
python scripts/generate_release_topology.py `
  --check `
  --release 0.18.1 `
  --frozen-product-sha <40-hex-freeze-sha> `
  --prepared-swarm-sha <40-hex-prepared-sha> `
  --frozen-root <exact-frozen-checkout> `
  --frozen-topology release_topology.frozen.v1.json `
  --frozen-topology-sha256 <64-hex-frozen-topology-digest> `
  --output release_topology.v1.json
```

Every invocation performs full JSON-schema validation before semantic checks;
the pinned validator is installed from `scripts/requirements-release.txt` by
the release and rolling-observation workflows with binary wheels only (Python
3.11 or newer, matching the generator's `tomllib` requirement). The v1
release field remains stable `X.Y.Z` and is passed through byte-for-byte. A
prerelease such as
`0.18.0-rc.1` is rejected by this stable topology contract rather than being
silently stripped or mapped to a VSIX version; an RC-specific mapping requires
the release-preparation authority to define that contract first.

The JSON schema is [`schemas/release_topology.v1.schema.json`](../../schemas/release_topology.v1.schema.json).

## Opt-in public checksum inventory

Use `--schema-version 2` on both generation and `--check` commands to select
[`release_topology.v2`](../../schemas/release_topology.v2.schema.json). Omitting
the option selects v1, including when checking an existing file. A mismatched or
unsupported selection fails; the checker does not infer an upgrade from input.

The required `checksum_assets` row identifies:

- public asset `SHA256SUMS`;
- algorithm `sha256`;
- channel `github_release`;
- sorted, unique `archive_targets` covering exactly `binary_targets`.

Resolve each covered archive filename through its `binary_targets` row. This
keeps version-derived names under the existing archive authority and lets a
version-only prepared transition preserve the checksum denominator. The public
file covers release archives, not VSIX, SBOM, internal manifests, itself, or
archive-local `SHA256SUMS.txt`. The latter remains a required archive member
whose entries cover the enclosed binaries.

The generator checks the complete recognized consolidated-checksum producer
body in `.github/workflows/release.yml`, including duplicate filename refusal,
copy destination, both archive formats, sorting, hash algorithm, and output
name. Recognition binds that step to the candidate job's build dependencies,
Linux runner, and complete ordered prefix: checkout, Rust setup, archive
download (`perllsp-*` into `artifacts`), build-identity evidence download, and
the read-only archive listing. Extra, missing, reordered, or altered prefix
steps fail closed; isolated presence of the download and producer is insufficient.
Unsupported workflow or job run defaults, conditional/container candidate
contexts, changed download inputs, and global environment mappings other than
the recognized release settings fail closed. It does not execute workflow code. An unrecognized producer shape fails
closed until reviewed with the focused execution oracle; changing a step name
or retaining isolated command strings cannot establish that contract.

The inventory declares expected subjects. It does not contain their built
digests, prove successful checksum generation or publication, or complete the
SBOM, attestation, Docker, or release-readiness contracts. #6067 remains the
topology owner; #4145 owns checksum production and #8970 owns Docker identity.

## Version compatibility and recovery

Generate fresh v2 frozen and prepared authorities after selecting the new
contract. Frozen and prepared versions must match in both directions, and their
selected schema bytes must be identical, tracked, and clean. A v1 frozen
manifest cannot be used to prepare v2, or vice versa. Preserve old v1 bytes and
digests as their original authority rather than editing or relabeling them.

The generator emits integer schema identifiers. The canonical Python validator
retains JSON Schema's integral-number semantics, including historical `1.0`;
booleans, strings, fractional numbers, and unsupported versions are rejected.
All six topology file boundaries inspect the original top-level schema number
before ordinary JSON decoding. Mathematically exact forms such as `2.00`,
`2e0`, and `20e-1` remain valid; near-integral literals such as
`2.0000000000000001` and ambiguous duplicate schema fields fail closed. JSON
parsing owns escaped field names and nesting. Admission never rewrites the
bytes used for frozen authority or consumer digests.
Build identity, public-claim binding, install-transition, and public-beta
experience consumers accept their supported v1/v2 projections while retaining
existing digest, source, target, and status checks. Public-beta child envelopes
must name `release_topology.v1` for source schema 1 or `release_topology.v2` for
source schema 2. These bounded consumers do not gain checksum-completeness
authority merely by accepting v2.

Generation or validation failures return a nonzero result; semantic or source
failures report `release-topology: NOT_PROVEN`. Restore the matching committed
inputs or regenerate the correct frozen/prepared pair, then rerun the same
explicit selection. There is no automatic downgrade. Rolling back the opt-in
v2 implementation leaves v1 evidence and default callers intact.

## Focused proof

```powershell
python -m unittest scripts.test_generate_release_topology scripts.test_release_build_identity
python scripts/test_release_terminal_manifest.py
python scripts/tests/test-validate-public-release-claims.py
cargo test -p xtask --locked --example install_transition --example public_beta_experience
```

The checksum execution oracle requires Linux Bash and coreutils, or WSL Bash
when invoked from Windows. It executes the actual selected producer body with
target-derived fixture files of both archive formats, compares exact checksum
lines, and challenges omitted ZIP coverage, a different hash algorithm,
renamed output, and duplicate archive names. Missing Linux/Bash support is a
proof failure, not a skipped pass. This test-only requirement does not change
the generator's static validation or platform behavior.

The real-Git CLI fixture verifies v1/v2 generation, checking, deterministic
prepared output, schema/source binding, and crossed-version refusal with
controlled Cargo metadata. It is not a built artifact or real release receipt.
