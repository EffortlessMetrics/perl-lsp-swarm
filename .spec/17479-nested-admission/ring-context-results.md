# #17479 / #17483: Cargo package-context handoff

The outer and nested Cargo invocations can receive different caller package metadata even when their bound plans, tools, configuration, roots, features and profiles agree. The bounded repair normalizes the same 17 Cargo-generated package metadata fields at root admission with a nested plan and at leaf rendering. It preserves custom inputs (including `CARGO_PKG_USER_SETTING`), bound configuration, resources, tool identities, network inputs, compiler flags and ordinary admission without a nested plan. Cargo reconstructs actual package metadata for each build script, rustc and target process.

Cargo 1.95 [injects package context for target executables](https://github.com/rust-lang/cargo/blob/rust-1.95.0/src/cargo/core/compiler/compilation.rs#L436-L449), and [`cargo run` uses that target process](https://github.com/rust-lang/cargo/blob/rust-1.95.0/src/cargo/ops/cargo_run.rs#L108). Build-script `rerun-if-env-changed` fingerprints [read configured values or the invoking Cargo environment](https://github.com/rust-lang/cargo/blob/rust-1.95.0/src/cargo/core/compiler/fingerprint/mod.rs#L904-L915). Ring 0.17.14 watches `CARGO_MANIFEST_DIR` and several package name/version fields. Inheriting xtask's runtime package context into another Cargo invocation therefore creates a concrete freshness hazard. This is a normalization contract repair, with native cache reuse still **NOT_PROVEN**.

The ring library stamp is now empty and its rlib absent after cancellation. Cargo [truncates a dirty unit's stamp before compilation](https://github.com/rust-lang/cargo/blob/rust-1.95.0/src/cargo/core/compiler/fingerprint/mod.rs#L438-L547). The 14-byte `dep-lib-ring` file retains the earlier successful compilation timestamp; it was not cleared by the cancelled attempt.
